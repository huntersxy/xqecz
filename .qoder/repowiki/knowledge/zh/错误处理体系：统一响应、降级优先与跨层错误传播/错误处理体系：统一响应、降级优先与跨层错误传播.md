## 1. 系统/方法概述
本仓库采用「分层 + 契约化」的错误处理策略：
- NestJS API 层使用框架内置异常（NotFoundException、BadRequestException、ForbiddenException）配合全局过滤器，统一返回 `{ code, message, data }` 格式。
- Go Worker 层通过 gRPC 的 `success` + `error` 字段传递业务错误，不抛 rpc error，由调用方根据 `success` 判断并降级。
- 前端通过 ofetch 拦截器集中处理网络错误、401 未授权、非 2xx 业务错误，并以统一的 `ApiError` 类型向上抛出，由调用处统一弹出提示。
- 跨进程通信（NestJS ↔ Worker）遵循 AGENTS.md 中「降级优先」约束：外部依赖缺失即降级，gRPC 永不返 rpc error。

## 2. 关键文件与包
- `packages/api/src/worker/worker.service.ts` — gRPC 客户端封装，超时与错误统一转为 `{ success: false, error }` 对象
- `packages/api/src/content/content.service.ts` — 媒体处理链路（缩略图/压缩/S3/OG 抓取），每步 try/catch 仅告警不影响后续步骤
- `packages/frontend/src/api/index.ts` — ofetch 实例、请求/响应错误拦截、统一 `ApiError` 类型、401 自动登出跳转
- `proto/xqecz.proto` — gRPC 接口定义，所有响应体均含 `success` + `error` 字段
- `AGENTS.md` — 明确「统一响应 `{ code, message, data }`」「降级优先」「gRPC 永不返 rpc error」等约束

## 3. 架构与约定
- **统一响应格式**：API 层对外返回 `{ code, message, data }`，前端 `pickServerMessage` 兼容 `{message}` 与 `{data:{message}}` 两种结构，确保错误文案一致透出。
- **gRPC 错误契约**：Worker 所有 RPC 响应包含 `success`（bool）和 `error`（string），NestJS 侧 `callWithTimeout` 将 TimeoutError 转换为 `{ success: false, error: 'timeout after ...' }`，其他错误原样抛出。
- **降级优先**：推荐读取 Redis 失败时回退到 DB；S3/Tinify/Worker 缺失即降级本地路径或跳过；缩略图/压缩/S3 任一阶段失败仅 console.warn，不中断流水线。
- **异步错误隔离**：`processMedia`、`processLinkPreview`、`refreshRecommend` 等异步操作使用 `void this.xxx().catch(...)` 模式，确保主流程不受影响。
- **前端错误分类**：网络错误、取消错误、后端业务错误通过 `ApiError.name === 'ApiError'` 区分，401 自动触发登出并跳转登录页。

## 4. 约定与约束
- **统一响应格式**：`{ code, message, data }` 为全仓约定（见 AGENTS.md 第 122 行）。
- **降级优先**：外部依赖缺失即降级，gRPC 永不返 rpc error，只返 `success=false` + `error` 文本（见 AGENTS.md 第 124 行）。
- **NestJS 独占 DB/Redis**：Worker 不直连数据库，错误边界清晰（见 AGENTS.md 第 120 行）。
- **前端统一错误通道**：`request()` 与 upload 的 onload 非 2xx 分支共用 `apiError`，保证错误展示一致（见 `packages/frontend/src/api/index.ts` 第 106-132 行）。
- **gRPC 超时默认 30s**：可通过 `WORKER_CALL_TIMEOUT_MS` 环境变量覆盖（见 `worker.service.ts` 第 6 行）。
- **软删除**：所有删除写 `deleted_at`，TypeORM 查询自动附加过滤条件（见 AGENTS.md 第 123 行）。
